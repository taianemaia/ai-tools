**Title:** Add Rate Limiting to the Public API

**Story:** As a platform operator, I want to enforce rate limits on the public API, so that the service remains stable and available for all consumers, and abuse or runaway clients cannot degrade performance for legitimate users.

**Assumptions:** Authenticated clients: 1,000 req/min per API key. Unauthenticated: 60 req/min per IP. Sliding 1-minute window. Shared Redis store. 20% burst allowance. Retry-After in seconds.

**Acceptance Criteria:**
1. Every response includes X-RateLimit-Limit, X-RateLimit-Remaining, and X-RateLimit-Reset headers.
2. Exceeding the limit returns HTTP 429 with a JSON body { "error": "rate_limit_exceeded" } and a Retry-After header.
3. Authenticated clients are limited per API key; unauthenticated per IP (honoring X-Forwarded-For).
4. Counters are shared across all server instances (Redis-backed).
5. 20% burst allowance enforced per second before throttling.
6. Limits documented in public API reference.
7. 429 responses are fail-fast; other clients unaffected.
8. Internal service API keys are exempt.
9. A metric (api.rate_limit.exceeded) is emitted on every 429, tagged by client type.

**INVEST:** Independent (middleware layer), Negotiable (limits are starting points), Valuable (reliability + fairness), Estimable (known patterns, existing Redis), Small (no UI/billing in scope), Testable (all criteria are objectively verifiable via integration tests).

**Story Points:** 5 — moderate complexity, low risk. Redis already in stack; cross-instance consistency adds effort; documentation and metrics bounded in scope.

**Out of scope:** Self-serve quota management, tiered limits by pricing plan, per-endpoint limiting, CDN-level DDoS mitigation.
