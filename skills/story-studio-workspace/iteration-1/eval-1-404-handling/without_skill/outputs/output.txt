**User Story: 404 Handling for PDP Routes Matching AEM Rules**

As a visitor to the website,
I want to see a meaningful 404 page when I land on a PDP URL that does not match any known product,
So that I understand the page does not exist and I am guided back to valid content, consistent with the rest of the site experience managed by AEM.

**Acceptance Criteria**
1. When a user navigates to a PDP route (e.g., `/product/{slug}`) where the slug does not match any product, the application returns HTTP 404.
2. The 404 response follows AEM rules: URL pattern matching logic, page template/design, and any redirect/fallback behavior all mirror AEM configuration.
3. The HTTP response header returns 404 (no soft 404s returning 200 OK with error content).
4. Search engine crawlers receive the correct 404 to prevent incorrect indexing.
5. Covers all PDP 404 scenarios: deleted/unpublished products, malformed slugs, valid structure but no matching product.
6. An error monitoring event is emitted when a PDP 404 occurs.
7. Automated tests (unit/integration) verify non-existent PDP routes return 404 with the correct error page.

**Out of Scope**
- Changes to AEM 404 rules themselves
- 404 handling for non-PDP routes

**Assumptions**
- AEM 404 rules are documented and accessible to the team.
- PDP route pattern is known (e.g., `/product/{slug}`).
- The frontend supports server-side rendering with HTTP status code control.

**Definition of Done**
- Code implemented, reviewed, and merged.
- 404 status verified in response headers for non-existent PDPs.
- Rendered 404 page matches AEM-defined design.
- Automated tests pass in CI.
