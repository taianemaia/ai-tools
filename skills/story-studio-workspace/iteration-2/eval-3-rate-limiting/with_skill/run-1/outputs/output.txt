Feature description: add rate limiting to the public API


[STORY WRITER - turn 1]

STORY:

Story: As an API consumer, I want the public API to enforce rate limits on requests, so that the service is protected from abuse and remains available to all users.

Acceptance Criteria:
- The API tracks the number of requests made by each client within a rolling time window.
- When a client exceeds the allowed request limit, the API returns an HTTP 429 (Too Many Requests) response.
- The 429 response includes a `Retry-After` header indicating when the client may resume requests.
- Requests within the allowed limit are processed normally with no change to existing behavior.
- Rate limiting is applied only to public API endpoints.

INVEST Note: The story is independent, valuable, and testable; it is estimable given common rate-limiting patterns; the scope is small enough to implement in a single sprint, though the specific threshold is still open.

Story Points: 5 — Requires middleware or gateway configuration, error response formatting, and testing across edge cases, but no new data models.

Open Questions:
- Rate limit threshold — stakeholder confirmed the limit should protect the API from abuse but has not yet specified the exact number of requests per window (e.g., 100 requests per minute per client).
- Time window — the duration of the rolling window (e.g., per minute, per hour) has not been specified.
- Client identification — it is unclear whether clients are identified by API key, IP address, or another mechanism.
